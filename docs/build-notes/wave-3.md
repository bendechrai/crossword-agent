## T42 repair pass
**Deviations:**
- Added an exported `RepairPassOptions extends RepairOptions` (all new fields optional, so `repair` stays assignable to the frozen `RepairFn`, asserted by a test) carrying `chargeBudget`, `style`, `title`, `candidatesPerAsk`, `samples` and `sampleIndex`. Reason: `RepairFn` is frozen and passes neither `SearchHooks` nor the puzzle, yet the orchestrator note requires charging `hooks.chargeBudget('repairCalls', 1)` and every `CandidateRequest` needs a style/n/samples the `Grid` does not hold. The contract change that would make this first-class is adding those to `RepairOptions` (or a `hooks` parameter to `RepairFn`) in `src/solver/types.ts`.
- A proposal re-asks tier 1 only for its anchor slot; a crossing slot whose word also changes is scored from the `peek` ledger. Reason: the task decision caps a proposal at one service call, and T34's `getCandidatesBatch` throws for any purpose other than `seed` (B3), so scoring several affected slots with fresh asks is impossible within one call.
- Distance-2 letter pairs are drawn from the peek-plausible letters at each offset plus the word-list neighbours returned by `WordList.match` on the two-wildcard pattern, rather than the full 625-entry alphabet cross-product. Reason: the exhaustive form is quadratic per offset pair per slot (~600k gate checks per round on a 15x15) and every pair outside that union fails the gate anyway; distance-1 stays an exhaustive A-Z sweep so a gate rejection is observable (acceptance 2).
- The word-list fill of still-empty slots runs even when `maxCalls` or a budget cap ended the scoring loop. Reason: it costs no service call and the spec's cap behaviour is to end a phase gracefully rather than throw away free work.

**Notes for later waves:**
- T44: `repair` is a plain exported async function, not a `const: RepairFn`. It is assignable to the `RepairFn` slot in `SolveDeps` (a test pins that), and its real parameter type is the exported `RepairPassOptions`. Pass `chargeBudget: hooks.chargeBudget` through it so `repairCalls` is charged and the phase ends itself, plus `style`, `title`, `candidatesPerAsk`, `samples` and `sampleIndex` from the puzzle/profile/`SolveOptions.repeatIndex`; every one is optional and defaults (`style: 'unknown'`, `n: 10`, `samples: 1`, `sampleIndex: 0`) so an unwired call still produces well-formed requests.
- T44: `repair` charges the budget itself before each scoring call and returns as soon as `chargeBudget` reports any crossed cap (not only `repairCalls`), so a run-global usd/tokens/wallMs cap crossed elsewhere also ends the repair phase on the next proposal. It never throws; the caller emits `phase:start('repair')`/`phase:end` and `budget:hit`.
- T44/T39: one accepted proposal emits one `repair:accept` per slot whose word changed (the anchor and any assigned crossing), all with the proposal's own per-slot edit distance, `tier: 1` and `producedBy: 'tier1'` - `Candidate` carries no model id, the same choice T37 made for `search:assign`. Word-list fills emit `tier: 'wordlist'`, `producedBy: 'wordlist'`, with `before` set to the slot's pattern (so `before` contains `?` characters there) and `editDistance` equal to the number of blanks filled.
- T44: `RepairResult.proposals` counts every `repair:propose` event, including the ones rejected by the gate, so it is in the hundreds even on a 3x3 (distance-1 is an exhaustive A-Z sweep per filled cell per assigned anchor). `accepted` counts accepted proposals plus word-list fills, not `repair:accept` events. `repair:propose`/`repair:reject` are level-2 events, so a `-vv` run of a 15x15 will see a lot of them; if that turns out to be too loud, the cheapest fix is to emit `repair:propose` only for gate-passing proposals and record gate failures in the result instead.
- T43: this task never imports `src/validate/wordlist.ts`; it codes against the `WordList` interface in `src/validate/types.ts` and reads `loaded` to decide whether the word-list arm of the gate is live. It relies on `match(pattern, limit)` returning matches best-first and on `?` being the only wildcard, and it calls `match` with a two-wildcard pattern (e.g. `"?O?"`) for distance-2 enumeration, so `match` must handle several wildcards, not just one.
- T44/T18: repair never reads `DomainStore`, so the suspect marks left by an AC-3 wipeout, a policy give-up or a budget-exhausted termination pass are invisible to it. If a later wave wants repair to prioritise suspect slots, the store (or a suspect-slot list) has to be passed in, which needs a `RepairFn` contract change.
- A slot the word list fills is scored with `wordList.score(word)` for the purposes of any later comparison inside the pass; the run record's per-slot `producedBy` should come from the `repair:accept` event, which is authoritative.
